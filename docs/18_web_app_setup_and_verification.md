# 독립 웹앱 실행과 검수

갱신: 2026-09-06 KST. **웹 전환 P0·P1·P2-A·P2-B 자동 검증 완료 / P2-C·P3 대기**.

## 실행

기존 프로젝트 의존성 설치 후, 저장소 루트에서:

```sh
pnpm app:start
```

1. 웹 빌드 후 동일 프로젝트·현재 빌드와 맞는 서버인지 확인한다.
2. 서버가 없으면 콘텐츠 DB를 안전하게 백업하고 `127.0.0.1:3719`에 시작한다.
3. [내 콘텐츠 작업실](http://127.0.0.1:3719/app/)을 열고 터미널에 표시된 일회용 코드를 입력한다.
4. 연결 코드는 5분·1회 사용이다. 웹 세션은 최대 8시간이고 설정에서 종료할 수 있다.

이미 실행 중인 최신 서버에 다시 연결할 때:

```sh
pnpm app:pair
```

- 긴 Local Core 토큰·OAuth 토큰을 웹 화면에 붙여넣지 않는다.
- `localhost` 대신 `127.0.0.1` 주소를 사용한다. 다른 Origin/Host는 거부한다.
- 구버전이나 다른 서버가 포트를 사용하면 실행을 중단하고 안내한다. 다른 프로세스를 임의 종료하지 않는다.
- 터미널 종료 시 이 실행기가 시작한 서버도 종료된다. 이미 실행 중인 서버를 재사용한 경우 종료하지 않는다.
- 기본 포트 변경은 `LOCAL_CORE_PORT`로 설정한다. 서버와 코드 발급기에 같은 환경을 적용해야 한다.

웹 내부 메뉴 이동은 같은 탭이며 작성 화면은 유지된다. 원문 사진 링크 등 외부 이동에는 새 탭임을 표시한다.
`수정 내용 저장`, `네이버에 임시저장`, `공개 완료 사실 등록`은 서로 다른 행동이다.

## 아직 이관하지 않은 기능

- 확장 현재 탭 수집 결과를 웹에 전달하는 연결
- 샘플 모드, 전 기능 E2E·실계정 인수. **`pnpm app:demo`는 아직 없다.**

위 기능은 기존 확장에서 제거하지 않았다. 웹 메뉴가 생겼다는 이유만으로 전체 이관 완료라 판단하지 않는다.

## 인증·저장 경계

- 브라우저: HttpOnly·SameSite=Strict 쿠키, 웹 요청은 같은 Origin만 사용한다. 쿠키 기반 변경 요청에는 정확한 Origin와 별도 요청 헤더가 필요하다.
- 서버: 코드/세션 원문 대신 digest·만료·Origin을 별도 권한 0600 인증 DB에 보관한다. 코드 소비와 세션 발급은 트랜잭션으로 처리한다.
- 인증 DB: 콘텐츠 DB 옆의 `.<DB파일명>.web-auth.sqlite3`; Git 제외. 확장 `X-Local-Token`은 기존과 호환된다.
- localhost HTTP 전용 설계다. LAN·클라우드로 노출하거나 인증/Origin 검사를 해제하지 않는다.
- 웹 localStorage에는 블로그 ID·태그·허용 옵션만 저장하며 토큰·원고 본문을 넣지 않는다.
- 원고 저장의 `expected_version`은 최신 웹/확장에서 보낸다. 구형 클라이언트의 미전송 요청은 호환되므로 구형 확장까지 완전한 충돌 보호를 보장하지 않는다.
- 네이버 저장도 요청한 원고 버전을 확인한다. 통신 실패로 생성 여부가 불명확하면 재요청을 막고 `기존 임시저장 작업 다시 확인`으로 조회한다. 새 Job이 확인되기 전에는 빈 조회 결과만으로 재실행을 허용하지 않는다. 명시적 409 버전 충돌은 불명확한 응답과 구분한다.

## 검증

```sh
pnpm test:web       # 웹 UI·공유 클라이언트·작성/편집 회귀
pnpm test:parity    # F01~F30 구조 보존표 검사 — 기능 동등성 전체 PASS 아님
pnpm verify        # 기존 Python·확장 전체 + 웹 테스트/빌드 + 빈 DB migration
```

현재 자동 검증: Python 297 + Extension 75 + Web 114 = **486건 통과**. smoke 4건 제외, 기존 Starlette/httpx deprecation 경고 1건.

일반 인앱 브라우저 + 격리 검수 DB에서 연결→목록→원고 편집→v3 저장→새로고침/재열기를 확인했다. 320/430/768/1280/1440px에서 확인한 작성 화면의 페이지 전체 가로 넘침은 없었다.

- 실제 AI 생성은 이번 구현의 UI/API fixture 회귀로 확인했다. 이번 실행에서 실제 모델의 글 품질을 새로 인수한 것은 아니다.
- 이번 웹 UI의 실제 네이버 임시저장·실계정 성과 표·전체 키보드/접근성 인수는 아직이다.
- 검수 DB는 운영 DB와 분리했다. 샘플 모드를 구현했다는 의미는 아니다.

## 근거·플랜 및 성과 개선 사용 순서 (P1)
1. 글쓰기의 **근거와 플랜으로 쓰기**에서 주제를 입력하고 **주제 분석**을 누른다.
2. **근거 자료 불러오기**에서 출처·수집 시각·결측·경고를 확인하고 사용할 자료를 선택한다.
3. **선택한 근거 승인**으로 새 승인 버전을 저장한다. 선택을 다시 바꾸면 승인 상태로 작성할 수 없다.
4. 플랜 하나를 고르고 **승인 근거로 글 만들기** 또는 **글 뼈대만 만들기**를 누른다. 글 뼈대는 완성 글이 아니다.
5. 같은 화면에서 편집·새 버전 저장·근거 버전 조회·네이버 임시저장 작업 확인을 이어간다.
6. 성과의 **글 개선하기**는 원래 키워드/참조 원고/추천 ID를 메모리로 전달한다. 제목 개선·본문 최신화·후속 글 모두 선택할 수 있다. 준비만으로 AI를 호출하지 않는다.
7. 원고 저장 응답을 받은 요청의 추천만 완료 처리한다. 완료 표시만 실패하면 글을 다시 생성하지 않고 표시만 재시도할 수 있다. 주제를 수동 변경하면 추천·참조 원고·자동 메모 연결을 해제한다.

P1 브라우저 검수: 외부 소켓 연결·AI·Publisher를 차단한 임시 검수 서버와 별도 DB/쿠키로 분석→근거 선택→v2 승인→구조 원고 생성→편집 v2 저장→새 페이지 재열기 및 근거 v2 연결을 확인했다. 320/430/768/1280/1440px에서 플랜/근거/원고 화면의 전체 가로 넘침 없음. 이는 임시 테스트 장치이며 제품의 `app:demo`나 P3 전 기능 검수 환경을 구현한 것은 아니다.

## P2-A 반영 (2026-09-06)

키워드 찾기에 최신·급상승/연관어/맵/의도/독자/입찰/관심/분야별 자료를 연결했습니다. 메뉴 위치와 앱 설정 의미, 데이터 출처 한계는 [키워드·메뉴 검토](19_web_keyword_and_menu_review.md)를 참조하세요. 최신 자동 회귀는 Python291 + Extension74 + Web62 = 427건입니다. 성과 상세 집계·가져오기(P2-B), 확장 수집 연결(P2-C), 정식 샘플(P3)은 아직 남아 있습니다.

## P2-B 전체 재검토 반영 (최신)

앞의 P1/P2-A 기록 이후 성과 상세 이관을 완료했습니다. 성과 → 자료 가져오기·채널에서 종류/채널/기간을 고르고 표를 미리 확인한 뒤 저장하세요. 성과 확인·개선은 선택 채널의 자료만 보여줍니다. 광고 계정 성과는 별도 확인 후 조회합니다. 실제 남은 작업은 P2-C·P3·실계정 인수이며 [전체 검토 결과](20_full_function_review_20260906.md)를 기준으로 확인하세요.

## 화면 테마 (2026-09-06 추가)

1. 웹 상단 **앱 설정 → 화면 테마**를 엽니다. 로컬 앱에 연결하기 전에도 선택할 수 있습니다.
2. **시스템**은 기기의 다크/라이트 설정을 따르고, **라이트·다크**는 해당 화면을 유지합니다.
3. 선택은 즉시 반영되고 이 브라우저에 저장됩니다. 새로고침·다음 실행에서도 유지되며 다른 브라우저와는 자동 공유되지 않습니다.

미저장 원고·주제·성과 붙여넣기를 유지하고 테마 전환 자체로 서버 호출/AI 생성/네이버 저장을 하지 않습니다. 저장이 차단되면 화면만 바뀌며, 설정의 ‘테마 저장 다시 시도’를 사용하세요. Chrome 자체·네이버 편집기·확장 전체·사진은 변경하지 않습니다.

개발 및 검증 상세는 [다크 테마 계획](../dev-plan/implement_20260906_230626.md) 참조. 현재 Chrome 기본 폭에서 주요 화면·키보드 전환·새로고침을 확인했습니다. 새 탭 차단/viewport 미적용으로 지정 폭·샘플 차트/사진 시각 검수는 남아 있으며 전체 접근성 검증을 완료했다는 뜻이 아닙니다.
